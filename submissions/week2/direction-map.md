## 二、为什么不是纯 AI / 纯 Web3 问题？

### 分析方向 ①：Payment / Commerce / Settlement

**为什么不是纯 AI 问题？**

AI 能理解"帮我付款给供应商"的意图，能生成报价、选择支付路径、计算汇率——但它无法独立完成以下环节：
- **资金托管**：AI 没有"钱"，也无法强制锁定资金等待交付验收。没有智能合约 Escrow，预付款就是单方面信任。
- **不可篡改的收据**：AI 生成的付款确认可以被伪造或否认；链上交易哈希是唯一不可抵赖的证据。
- **跨主体结算**：多个 Agent、多个服务方之间的资金分配需要可信第三方或链上规则，AI 自己无法扮演可信仲裁者。

**为什么不是纯 Web3 问题？**

智能合约能托管资金、自动结算、提供不可篡改记录——但它无法独立完成：
- **意图理解**：合约只处理结构化的函数调用，无法理解"帮我找最便宜的方案付给供应商"这类自然语言需求。
- **动态谈判**：报价、条款协商、交付物定义需要理解上下文、匹配语义，这是 LLM 的能力范围。
- **异常处理**：交付失败、服务质量争议、仲裁需要语言理解和推理，合约只能处理预先编码的分支。

**结论**：Payment 场景需要 AI 做意图层、谈判层、异常判断，Web3 做执行层、结算层、审计层。两者缺一不可。

### 分析方向 ③：Wallet / Permission / Safe Execution

**为什么不是纯 AI 问题？**

AI 能评估"这笔操作是否合理"、能识别 Prompt Injection 企图——但：
- **执行层无法被 AI 自己约束**：如果 AI 判断"这笔交易有风险"，它无法阻止自己（或另一个 AI 进程）实际发出交易。约束必须在执行层（链上策略）硬编码。
- **权限边界需要密码学保证**：白名单、金额上限必须写进合约逻辑，不能只靠 AI 的"我会遵守规则"承诺。
- **撤销机制需要链上状态**：`revokeSessionKey()` 是链上操作，AI 无法在链下"吊销"一个密钥。

**为什么不是纯 Web3 问题？**

合约能强制执行白名单和金额上限——但：
- **风险动态评估**：合约只能处理静态规则（金额 > 500 USDC → 拒绝），无法理解"这个操作在当前市场环境下是否异常"。
- **意图模糊处理**：用户说"帮我赚最多的收益"，合约无法把模糊意图翻译成具体调用参数。
- **用户体验**：纯链上方案的交互是十六进制 calldata，需要 AI 层做自然语言桥接。

## 三、主方向选择：Payment / Commerce / Settlement

**选定方向 ①：Payment / Commerce / Settlement**

### 选择理由

1. **最具体的 AI × Web3 交叉点**：意图理解（AI）+ 链上结算（Web3）的分工最清晰，每一步都能写出具体的系统设计。
2. **有真实标准可对标**：x402、ERC-8183、MPP、ERC-8004 都有公开草案，不是纸上谈兵。
3. **最小 demo 可落地**：一个"Agent 请求服务 → x402 付款 → 获取结果"的闭环可以用现有工具实现（或伪代码描述）。
4. **覆盖本周最高分任务**：进阶实践 x402 + CAW（40 分）直接在这个方向上展开。
5. **与 Week 1 基础衔接**：Machine Payment（Day 5 已读）、Agent Wallet（Day 3 已读）、智能合约（已部署 Hello.sol）是直接前置知识。

### 本周主线场景

> **「一个 AI Agent 作为服务消费方，向提供受 x402 保护的 API 服务方发起请求，识别付款要求，通过 CAW/Pact 在预算范围内完成支付，获取服务结果，并留下可审计的完整记录。」**

### 暂不选择的方向（Backlog）

| 方向 | 暂不选择的原因 |
|------|--------------|
| ② Identity / Reputation | 标准（ERC-8004）仍处于草案阶段，真实可验证的链上身份系统尚不成熟；更适合作为 Payment 方向的配套（「谁在付款」的身份层），而非独立主线 |
| ④ Privacy / Security | ZK Proof 技术门槛较高（需要 Circom/Noir 等专业工具），在 ≤1h/天的时间约束下难以产出可运行 demo；安全设计会作为 Payment 方向的风险层覆盖 |
| ⑤ Dev Tooling | 偏基础设施，产出更多是工具评测而非系统设计；适合在其他方向 demo 实现过程中自然覆盖 |
| ⑥ Governance | 政治/协作逻辑强，技术抓手弱；链上投票合约的 AI 集成目前案例少，验证标准模糊 |

## 四、主方向核心问题拆解（预览）

> 详细展开见 `week2-proposal.md`

| 维度 | 内容 |
|------|------|
| **参与方** | 服务消费方 Agent、服务提供方（API/AI 推理节点）、预算管理层（CAW/Pact）、链上结算合约、人类用户（审批高风险操作） |
| **核心流程** | 请求 → 402 响应 → 识别付款要求 → 预算检查 → 支付意图 → 链上转账 → 服务交付 → 收据存证 |
| **AI 作用** | 解析 402 响应头、匹配服务价格与预算、异常识别、触发人工确认 |
| **Web3 机制** | ERC-20 转账、x402 收款验证、链上 Escrow、CAW 预算策略、交易哈希作为收据 |
| **自动化边界** | 小额（< 阈值）可自动执行；大额、新服务方、频率异常须人工确认 |
| **主要风险** | 服务方伪造 402 响应、付款后不交付、Prompt Injection 操控支付路径、链上 gas 波动导致预算穿透 |
