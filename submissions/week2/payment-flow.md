## 一、问题定义：为什么 AI Agent 支付是个难题？

传统支付假设人类在场：人看到账单 → 人决策 → 人点击付款。  
AI Agent 支付打破了这个假设：

| 传统支付 | Agent 支付 |
|---------|-----------|
| 人类理解意图 | Agent 解析意图（可能出错） |
| 人类评估风险 | Agent 自动决策（可能被操控） |
| 银行/支付宝做信任背书 | 无可信第三方，需链上机制 |
| 事后可争议、退款 | 链上交易不可逆，需前置保护 |

**核心矛盾**：谁先动？

- 消费方先付 → 服务方可能不交付（跑路）
- 服务方先交付 → 消费方可能不付款（赖账）
- 解法 → **链上 Escrow 作为中间层**，资金锁定 + 条件释放

## 二、参与角色

```
┌─────────────────────────────────────────────────┐
│                   人类用户                        │
│  下达高级指令 / 审批高风险操作                     │
└────────────────────┬────────────────────────────┘
                     │ 指令
                     ▼
┌─────────────────────────────────────────────────┐
│              消费方 Agent（Consumer Agent）       │
│  意图解析 / 构建请求 / 触发支付 / 验收交付物        │
└──────┬──────────────────────────┬───────────────┘
       │ 请求服务                  │ 支付指令
       ▼                          ▼
┌─────────────────┐    ┌──────────────────────────┐
│  服务提供方 API  │    │  预算管理层（CAW / Pact） │
│  执行任务        │    │  检查预算上限 / 生成授权   │
│  返回结果        │    └────────────┬─────────────┘
└────────┬────────┘                 │ 授权支付
         │                          ▼
         │               ┌──────────────────────┐
         │               │   链上结算层          │
         │               │  ERC-20 转账          │
         │               │  Escrow 合约          │
         └──────────────►│  交易哈希（收据）      │
                         └──────────────────────┘
```

| 角色 | 职责 |
|------|------|
| 人类用户 | 下达高级指令；审批大额/高风险操作 |
| 消费方 Agent | 解析意图、构建请求、触发支付、验收交付物 |
| 服务提供方 | 提供受 x402 保护的 API；执行任务；返回结果 |
| CAW / Pact | 预算管理层；检查授权范围；生成支付意图 |
| 链上结算合约 | 资金托管；状态管理；条件触发释放 |

## 三、最小支付流程（x402 + Escrow）

### 3.1 正常流程

```
消费方 Agent                服务提供方 API            链上合约
      │                           │                      │
      │──── GET /api/service ────►│                      │
      │                           │                      │
      │◄─── 402 Payment Required ─│                      │
      │     (X-Payment: amount,   │                      │
      │      token, address)      │                      │
      │                           │                      │
      │── 检查预算（CAW/Pact）──   │                      │
      │   ✅ 在预算范围内          │                      │
      │                           │                      │
      │──────────────── lock(amount) ──────────────────►│
      │                           │                      │ LOCKED
      │                           │                      │
      │──── GET /api/service ────►│                      │
      │     (X-Payment-Tx: hash)  │                      │
      │                           │──── verify(hash) ──►│
      │                           │◄─── ✅ confirmed ────│
      │                           │                      │
      │◄─── 200 OK + Result ──────│                      │
      │                           │                      │
      │── 验收结果 ──              │                      │
      │   ✅ 符合预期              │                      │
      │                           │                      │
      │──────────────── release() ─────────────────────►│
      │                           │                      │ RELEASED
      │◄──────────────── tx_hash（收据）────────────────│
```

### 3.2 异常流程：服务方未交付

```
消费方 Agent                服务提供方 API            链上合约
      │                           │                      │
      │──── 资金锁入 Escrow ──────────────────────────►│ LOCKED
      │                           │                      │
      │──── 请求服务 ────────────►│                      │
      │◄─── ❌ 超时 / 无响应 ──────│                      │
      │                           │                      │
      │── 触发 dispute() 或 等待超时 ──────────────────►│
      │                           │                      │ DISPUTED
      │◄──────────────── 退款 tx_hash ─────────────────│ REFUNDED
```

## 四、状态机设计

```
              lock()
  PENDING ──────────► LOCKED
                         │
              deliver()  │  timeout()
                    ┌────┴────┐
                    ▼         ▼
               DELIVERED   DISPUTED
                    │         │
         release()  │         │  arbitrate()
                    ▼         ▼
               RELEASED   REFUNDED
```

| 状态 | 触发条件 | 资金归属 |
|------|---------|---------|
| `PENDING` | 合约部署，等待锁定 | 消费方 |
| `LOCKED` | 消费方调用 `lock()` | 合约托管 |
| `DELIVERED` | 服务方提交交付证明 | 合约托管 |
| `RELEASED` | Agent 验收通过，调用 `release()` | 服务方 |
| `DISPUTED` | 超时 / 验收不通过 | 合约托管 |
| `REFUNDED` | 仲裁结果：退款 | 消费方 |

## 五、x402 协议在流程中的位置

[x402](https://x402.org) 是基于 HTTP 402 状态码的机器支付标准，专为 Agent-to-API 场景设计。

### x402 响应头示例

```http
HTTP/1.1 402 Payment Required
X-Payment-Required: {
  "scheme": "exact",
  "network": "base",
  "maxAmountRequired": "1000000",
  "resource": "https://api.example.com/inference",
  "description": "Per-request inference fee",
  "mimeType": "application/json",
  "payTo": "0xAbCd...1234",
  "maxTimeoutSeconds": 300,
  "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
  "extra": { "name": "USDC on Base", "version": "1" }
}
```

### Agent 处理 x402 的逻辑

```
接收 402 响应
     │
     ▼
解析 X-Payment-Required 头
     │
     ├── amount > 预算上限？ ──► 停止，请求人工审批
     │
     ├── payTo 在白名单？ ──── 否 ──► 停止，请求人工确认
     │
     ├── 频率异常？ ──────────────► 停止，触发风控
     │
     └── ✅ 所有检查通过 ──► 调用 CAW/Pact 生成支付意图
                                    │
                                    ▼
                              链上转账 / Escrow lock()
                                    │
                                    ▼
                              携带 tx_hash 重发请求
```

## 六、AI 的角色边界

### AI 能做的（意图层 / 判断层）

| 能力 | 说明 |
|------|------|
| 意图解析 | 将自然语言指令转化为结构化支付请求 |
| 价格评估 | 判断 402 响应中的金额是否合理 |
| 交付验收 | 检查返回结果是否符合预期格式/内容 |
| 异常识别 | 发现频率异常、金额异常、Prompt Injection 企图 |
| 人工上报 | 超出自动化范围时触发人工确认 |

### AI 不能做的（执行层 / 信任层）

| 限制 | 原因 |
|------|------|
| 单方面释放 Escrow 资金 | 合约执行，AI 无权强制触发 |
| 自行修改预算上限 | CAW/Pact 策略由人类预先设定 |
| 证明自己的身份 | 需要链上 DID / 签名，不能自我声明 |
| 保证交付不可抵赖 | 需要链上哈希，AI 生成的日志可被伪造 |

## 七、自动化边界（人工确认点）

| 操作 | 自动执行 | 需人工确认 |
|------|---------|-----------|
| 读取链上状态、获取报价 | ✅ | — |
| 小额支付（< 预设阈值，已知服务方） | ✅ | — |
| 大额支付（> 预设阈值） | — | ✅ |
| 首次接入新服务方 | — | ✅ |
| 任何 `approve()` 操作 | — | ✅ |
| 触发 Escrow 争议 / 退款 | — | ✅ |
| 生成收据、写审计日志 | ✅ | — |

## 八、最小可验证 Demo 设想

**场景**：Agent 向一个受 x402 保护的推理 API 发送请求，完成付款并获取结果。

### 技术栈

| 层 | 工具 |
|----|------|
| Agent 逻辑 | Python / TypeScript + LLM |
| x402 处理 | `x402-axios` 或手动解析响应头 |
| 支付网络 | Base Sepolia（测试网）|
| 支付代币 | USDC（测试网）|
| Escrow 合约 | Solidity（Foundry 部署）|
| 预算管理 | CAW/Pact（或简化版：固定阈值检查）|

### Demo 最小闭环

```
1. Agent 发送 GET 请求 → 收到 402 响应
2. 解析响应头，确认金额在预算内
3. 调用链上合约 lock(amount, serviceAddress)
4. 携带 tx_hash 重发请求 → 收到 200 + 结果
5. 验收结果 → 调用 release()
6. 链上留存：lock_tx + release_tx + 审计日志
```

### 验证标准

- [ ] 链上可查 `lock()` 和 `release()` 两笔交易
- [ ] Agent 日志完整记录：意图 → 402 解析 → 预算检查 → 支付 → 验收 → 收据
- [ ] 超预算请求被正确拦截（不触发链上操作）
- [ ] 服务方未交付时，超时后资金可退回

## 九、主要风险与缓解

| 风险 | 缓解方式 |
|------|---------|
| 服务方伪造 402 响应（钓鱼） | 服务方白名单 + 首次人工确认 |
| Prompt Injection 操控支付路径 | 支付意图在独立层生成，不直接来自 LLM 输出 |
| 付款后不交付 | Escrow 锁定 + 超时自动退款 |
| Gas 波动导致预算穿透 | 预算检查含 gas buffer；设定硬上限 |
| Agent 身份被冒用 | DID + Session Key（见 `agent-identity.md`）|
